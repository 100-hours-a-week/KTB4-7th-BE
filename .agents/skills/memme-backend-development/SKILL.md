# memme 백엔드 개발 절차

공식 Notion 문서는 참고가 아니라 구현 범위의 승인 기준이다. API·스키마·의존성·V2/V3 범위를 추측해 채우지 않는다.

## 기능 구현 절차

1. 요구사항 분석 → API 정의서 → ERD 정의서 → 기존 코드 순서로 최신 내용을 확인한다. 기술·환경 변경이면 기술검토 및 스택도 확인한다.
2. 영향받는 요구사항, API, 테이블·컬럼, 오류·보안 규칙을 식별한다. 누락·충돌·V2/V3 전용 항목이면 사용자 승인 전까지 멈춘다.
3. 기존 GitHub Issue를 확인하거나 새 Issue를 만든다. 최신 `dev`에서 `feat/이슈번호-기능명` 브랜치를 만들고, 하나의 작은 기능 목적만 작업한다.
4. Request/Response DTO, Controller, Service, Repository, Entity의 책임을 분리한다. Entity를 API에 직접 노출하지 않는다.
5. 정상과 주요 예외 사례의 테스트를 작성하고 실행한다. Service 단위 테스트를 우선하며 필요하면 Controller/API 또는 Repository 테스트를 추가한다.
6. 관련 테스트와 전체 빌드를 실행한다. 실패하면 원인을 해결하며, 검증을 약화하거나 우회하지 않는다.

## PR 생성 절차

사용자가 “PR 올려줘”라고 요청한 경우에만 다음 절차를 사용한다.

1. 연결할 GitHub Issue를 확인한다. 기존 Issue가 없으면 한글 제목과 작업 범위·완료 기준을 포함한 Issue를 먼저 만든다.
2. 현재 브랜치가 `feat/이슈번호-기능명` 형식인지, 대상이 `dev`인지 확인한다.
3. `git status`와 diff를 확인해 하나의 작은 기능 단위인지, 관련 없는 파일이 없는지 검토한다.
4. 공식 요구사항·API·ERD 위반 여부와 API·DB 변경 여부를 확인한다.
5. 새·수정 테스트와 관련 기존 테스트를 실제 실행하고, 빌드 결과를 확인한다.
6. 한글 커밋 메시지와 한글 PR 제목·본문을 준비한다. 본문에는 주요 변경사항, 구현 기능, 테스트 내용·결과, API 변경 여부, DB 변경 여부, `Closes #이슈번호`를 포함한다.
7. commit·push·PR 생성 직전에 Issue, 생성 예정 브랜치, 커밋, PR 내용을 간단히 보여 주고 최종 승인 1회를 받는다.
8. 승인되면 추가 확인 없이 commit → push → `dev` 대상 PR 생성을 진행하고, Issue·브랜치·커밋·PR 제목·대상·테스트·빌드·링크를 보고한다.

## 환경·보안·CI 규칙

- Java 25 LTS, Spring Boot 4.1.1, MySQL 8.4 LTS(InnoDB), Spring Data JPA를 사용한다.
- `.env`는 로컬 전용이며 Git에 넣지 않는다. `.env.example`에는 실제 비밀값 대신 필요한 환경변수 이름과 안전한 예시만 둔다.
- CI의 테스트·빌드 실패를 우회하지 않는다. `dev` 병합 후 이미지는 AWS ECR에 저장되며, 운영 배포는 Cloud 담당자가 기록된 버전으로 수동 실행한다.

## 즉시 중단 신호

- “경로·스키마·의존성은 뻔하다.”
- “호환되니까 미리 추가하자.”
- “V2/V3 내용을 먼저 구현해도 된다.”
- “편하니까 실제 비밀값을 추적 파일에 넣자.”
- “테스트를 건너뛰고 PR부터 만들자.”

위 상황은 공식 근거·검증·승인이 부족하다는 뜻이다. 먼저 보완한다.
