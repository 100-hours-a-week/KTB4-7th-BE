# 날씨·매출 조회 캐시

연결 이슈: #346(검토), #605(공통 설정), #606(조회 Service).
2026-10-28 사용자 승인: 기존 Redis, 날씨 발표 시각별 공유, 매출 매장·기간·데이터 버전별 5분 TTL,
DB 갱신 커밋 후 이전 버전 재사용 차단, Redis 장애 시 원래 조회로 진행.

## 키와 저장 대상

환경 접두어는 `APP_CACHE_NAMESPACE`다. 운영 예시는 `memme:prod:v2:cache:v1`이다.
세션 직렬화와 키는 바꾸지 않는다. 값은 구체적인 DTO 타입의 JSON이며 임의 다형 타입 복원은 사용하지 않는다.

- `weather:forecast:v1:{nx}:{ny}:{baseDate}:{baseTime}`: 전체 페이지를 합친 KMA 단기예보 원본. TTL 3시간.
  새 발표가 조회 가능해지면 키가 바뀐다. 영업시간별 요약·특보는 이 캐시에 넣지 않는다.
- `sales:analysis:v1:{storeId}:{periodType}:{start}:{end}:{sourceDigest}`: 완료된 매출 분석/카테고리 DTO. TTL 5분.
  EMPTY나 분석 예외는 캐시하지 않는다. 권한 확인 후 조회하며 클라이언트 응답 계약은 바꾸지 않는다.

## 매출 데이터 버전과 일관성

버전의 기준은 Redis 카운터가 아니라 DB다. 같은 REPEATABLE_READ 트랜잭션에서 다음 원천을 읽어 SHA-256 지문을 만든다.

- 매장의 모든 일별 집계: ID, 날짜, 총액/메뉴액, 건수/수량, 커버리지 상태, 수정 시각.
  비교 기간이 조회 기간 밖에 있을 수 있어 매장 전체 날짜를 포함한다.
- 매장의 최대 주문 ID: 기존 업로드는 원천 주문·항목을 기간별 교체하고 새 ID를 부여한다.
  총액이 같더라도 메뉴 구성이 바뀐 재업로드를 구분한다.
- 요청 기간 예측: ID, 원본 업로드, 날짜, 예측/상하한, 모델 버전, 생성 시각.
- 해당 월 AI 인사이트: ID, 분석 ID, 상태, 실제 문장, 생성 시각.

그 지문으로 캐시를 읽거나 쓰고 분석도 같은 DB 스냅샷으로 계산한다. 갱신 전 독자가 뒤늦게 이전 결과를 저장해도
갱신 후의 독자는 다른 지문을 사용한다. 롤백된 변경은 다른 트랜잭션에 노출되지 않아 버전을 바꾸지 않는다.
원천 변경 시 Redis DEL 성공 여부에 의존하지 않으며, 사용되지 않는 구버전 값은 TTL로 제거된다.

보장 범위는 현재 애플리케이션의 원천 주문 교체와 집계/AI/예측 갱신 경로다.
원천 항목만 SQL로 직접 수정하고 집계를 재구축하지 않는 운영 작업은 지원하지 않는다.
분류 규칙·응답 의미를 바꾸는 별도 배포에서는 캐시 namespace 버전도 올린다.
DB replica를 사용하면 해당 DB의 가시성과 지연 정책을 따른다. DB 자체의 복제 지연을 해결하는 기능은 아니다.

## 설정과 운영 확인

- 기본 `APP_CACHE_ENABLED=false`. 캐시의 실제 활성화와 운영 Redis 변경은 이번 코드 작업에 포함하지 않는다.
- 연결은 Spring의 기존 `StringRedisTemplate` 설정을 사용한다. 연결/명령 타임아웃은 실제 Redis 설정을 확인한다.
- 운영 접두어를 환경별로 명시하고 용량·TTL을 확인한 후 활성화한다. 공유 Redis의 세션 데이터도 함께 고려한다.
- 기존 세션 ACL에 `GET/SET` 전체 권한을 넓히지 않는다. Redis 7 이상 selector 예:
  `(+get +set ~memme:prod:v2:cache:*)`. CI에도 같은 제한 selector를 적용한다.
- 읽기/쓰기/역직렬화 오류는 캐시 miss로 처리한다. 로그에는 오류 분류만 남기고 캐시 값·원문 URL·인증키는 남기지 않는다.
- 같은 키 만료 시 여러 인스턴스의 동시 원본 호출을 직렬화하는 분산 락은 이번 범위에 없다.
- 캐시 hit에도 DB 버전 조회는 수행한다. 원천 주문 항목 조회와 분석을 줄이는 방식이며 성능 수치는 별도 부하 측정이 필요하다.
